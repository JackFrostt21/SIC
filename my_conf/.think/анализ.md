### Что даёт Django 6.0 конкретно для этой задачи

Проверено импортом в установленном Django, не по памяти:

- **Шаблонные partials встроены в ядро**: теги `{% partialdef %}` и
  `{% partial %}` есть в `django.template.defaulttags`. Это прямо то, что нужно
  для HTMX: фрагмент (например, узел дерева или комментарий) описывается один
  раз внутри основного шаблона и оттуда же рендерится как ответ на HTMX-запрос.
  Внешний пакет `django-template-partials` не нужен.
- **`django.tasks`** — встроенный фреймворк фоновых задач. Переиндексация
  поиска, уведомления, тяжёлая обработка вложений уйдут туда, Celery на старте
  не потребуется.
- **`django.contrib.auth.middleware.LoginRequiredMiddleware`** и декоратор
  `login_not_required` — «закрыто по умолчанию» вместо расстановки
  `LoginRequiredMixin` на каждую view. Для корпоративной вики это правильная
  настройка безопасности по умолчанию.
- **`django.middleware.csp`** — Content Security Policy из коробки; понадобится,
  когда появится пользовательский HTML в контенте страниц.
- `django.contrib.postgres.search` доступен для полнотекстового поиска после
  перехода на PostgreSQL.

### 2.1 `spaces.Space`

Верхний уровень иерархии. Ключевые решения:

- `key` — короткий идентификатор в верхнем регистре (`ENG`), уникальный,
  используется в URL. Это Confluence-подход, и он лучше длинного slug: URL
  остаётся стабильным при переименовании пространства.
- `visibility` — `PRIVATE` (только участники) / `INTERNAL` (любой
  аутентифицированный сотрудник). Анонимного доступа в MVP нет.
- `homepage` — FK на `pages.Page`, nullable, `SET_NULL`. Задаёт стартовую
  страницу пространства.
- Удаление — только архивирование (`is_archived`); физическое удаление
  пространства с контентом слишком опасно для корпоративного инструмента.

```python
class Space(models.Model):
    class Visibility(models.TextChoices):
        PRIVATE = 'private', 'Приватное'
        INTERNAL = 'internal', 'Внутреннее'

    key = models.CharField('Ключ', max_length=16, unique=True)
    name = models.CharField('Название', max_length=200)
    description = models.TextField('Описание', blank=True)
    visibility = models.CharField('Видимость', max_length=16,
                                  choices=Visibility, default=Visibility.PRIVATE)
    homepage = models.ForeignKey('pages.Page', on_delete=models.SET_NULL,
                                 null=True, blank=True, related_name='+')
    created_by = models.ForeignKey(settings.AUTH_USER_MODEL,
                                   on_delete=models.PROTECT, related_name='created_spaces')
    is_archived = models.BooleanField('Архивировано', default=False)
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)
```

### 2.2 `spaces.SpaceMembership`

```python
class SpaceMembership(models.Model):
    class Role(models.TextChoices):
        OWNER = 'owner', 'Владелец'
        ADMIN = 'admin', 'Администратор'
        EDITOR = 'editor', 'Редактор'
        VIEWER = 'viewer', 'Читатель'

    space = models.ForeignKey(Space, on_delete=models.CASCADE, related_name='memberships')
    user = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE,
                             related_name='space_memberships')
    role = models.CharField(max_length=16, choices=Role)
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        constraints = [
            models.UniqueConstraint(fields=['space', 'user'], name='unique_membership_per_space'),
        ]
        indexes = [models.Index(fields=['user', 'space'])]
```

Роли — `TextChoices`, никаких строковых литералов по коду. Индекс `(user, space)`
нужен потому, что основной запрос системы прав — «какая роль у этого
пользователя в этом пространстве».

### 2.3 `pages.Page`

Самая нагруженная модель, поэтому по полям отдельно:

| Поле | Назначение и обоснование |
|---|---|
| `space` | FK, `PROTECT`. Пространство нельзя удалить, пока в нём есть страницы. |
| `parent` | FK на себя, nullable. Дерево. `PROTECT` + явное перевешивание детей в сервисе — см. раздел 6. |
| `title`, `slug` | `slug` уникален в пределах пространства. |
| `position` | Порядок среди соседей (целое с шагом 100). |
| `body` | Контент из редактора, уже прошедший санитизацию. Для CKEditor это HTML. |
| `body_format` | Чем создан `body`; сейчас всегда `html`. Поле нужно, чтобы сменить редактор позже без миграции схемы. |
| `text_content` | Плоский текст без разметки, только для поиска и превью. |
| `status` | `draft` / `published` / `archived`. |
| `version` | Номер текущей версии, инкрементируется под блокировкой строки. |
| `created_by`, `updated_by` | Авторство. `PROTECT` / `SET_NULL`. |
| `created_at`, `updated_at` | Даты. |

Ограничения на уровне БД: уникальность `(space, slug)`, проверка
`parent_id <> id`, уникальность `(space, parent, position)` с
`deferrable=Deferrable.DEFERRED`. Отложенные ограничения стали доступны именно
из-за выбора PostgreSQL: они проверяются в конце транзакции, поэтому не мешают
перенумерации соседей при перемещении страницы. На SQLite такой вариант был бы
невозможен.

#### Что меняется из-за выбора WYSIWYG (CKEditor 5)

- **Санитизация обязательна, и только на сервере.** Содержимое приходит из
  браузера и выводится через `|safe`, то есть автоэкранирование Django здесь
  отключено по определению. Без allowlist-фильтрации это хранимая XSS —
  срабатывающая у каждого читателя страницы, а не только у автора. Клиентскую
  проверку легко обойти прямым запросом к эндпоинту, поэтому `nh3` вызывается
  в сервисе сохранения. Allowlist составляется по фактически включённым плагинам
  редактора: чего редактор не умеет создавать, того в разметке быть не должно.
- **`text_content` появился именно из-за WYSIWYG.** Полнотекстовый поиск по
  HTML находит совпадения в именах тегов и атрибутах, то есть выдаёт мусор.
  Поэтому при сохранении извлекаем плоский текст и индексируем его. Это же поле
  даёт осмысленные превью в результатах поиска.
- **Отдельного `body_html` в MVP нет.** Изначально я планировал пару «источник +
  отрендеренный кэш», но CKEditor отдаёт сразу HTML: после санитизации оба поля
  содержали бы один и тот же текст, удваивая объём и на странице, и в каждой
  версии. Поэтому в `body` лежит уже безопасный HTML, готовый к выводу.
  Поле-кэш добавим только если появится редактор со структурным JSON — миграция
  будет чисто добавляющей и потому дешёвой.

Поскольку разработка идёт на PostgreSQL, к `Page` сразу добавляем
`search_vector = SearchVectorField(null=True)` и `GinIndex` по нему — поиск не
придётся переделывать отдельным этапом (см. §12).

### 2.5 `pages.Comment`

`page`, `author`, `body`, `created_at`, `updated_at`, `is_deleted`.
Мягкое удаление (`is_deleted`) вместо физического — так HTMX-обновление списка
остаётся предсказуемым, а история обсуждения не теряется. Поле `parent` для
веток обсуждения в MVP не заводим, но структура модели позволяет добавить его
одной миграцией.

### 2.6 `pages.Attachment`

`page`, `file` (`FileField` с `upload_to`-функцией, раскладывающей файлы по
`space_key/page_uuid/`), `original_name`, `size`, `content_type`,
`uploaded_by`, `created_at`.

Важно: файлы приватных пространств **не** отдаются напрямую через `MEDIA_URL`.
Скачивание идёт через view с проверкой прав. Хранилище абстрагировано Django
Storage API, поэтому переезд на S3 позже — вопрос настройки, а не схемы.

### 2.7 `pages.PageRedirect`

`space`, `old_slug`, `page`. Создаётся при переименовании slug, чтобы старые
ссылки в документации и переписке продолжали работать. Дешёвая таблица, которая
снимает основной минус «красивых» URL.

## 3. Организация Django apps

```
apps/
    core/        # без своих таблиц: абстрактные модели, миксины, template tags,
                 #  HTMX-хелперы, базовые шаблоны, дизайн-токены
    accounts/    # User (уже есть), логин/логаут/профиль
    spaces/      # Space, SpaceMembership, permissions.py
    pages/       # Page, PageVersion, Comment, Attachment, PageRedirect,
                 #  services/, forms.py
    search/      # без таблиц: view поиска и абстракция бэкенда поиска
```

Обоснование границ:

- **`spaces` и `pages` разделены**, потому что это два разных цикла изменений:
  пространства и участники меняются редко, страницы — постоянно. Плюс это
  освобождает имя `Project` для будущего Jira-модуля (важно: в текущем коде
  верхняя сущность называется `Project`, и если оставить это имя, будущий
  issue-tracking получит конфликт названий).
- **`Comment` и `Attachment` живут внутри `pages`**, а не в отдельных
  приложениях. Соблазн сделать «универсальные комментарии» через
  `GenericForeignKey` ради будущей Jira — это преждевременная абстракция:
  теряются FK-ограничения на уровне БД, ломается `select_related`, усложняются
  запросы. Когда появятся задачи, сделаем `AbstractComment` в `core` и
  конкретную модель `issues.IssueComment` со своим FK.
- **`core` без моделей** — только абстрактные базовые классы (`TimeStampedModel`)
  и общие шаблоны. Это не «слой ради красоты», а место, куда иначе начнёт
  расползаться дублирование.
- **`search` отдельным приложением** — логика запросов PostgreSQL FTS
  (`SearchVector`, `SearchRank`, ранжирование, подсветка) не относится ни к
  пространствам, ни к страницам, и её лучше держать в одном месте, а не
  размазывать по views. Приложение без своих таблиц.

Бизнес-логика: сервисный слой только там, где операция реально составная —
`apps/pages/services/pages.py` с `create_page`, `update_page` (создаёт версию),
`move_page`, `restore_version`, `archive_page`. Простой CRUD (например,
редактирование описания пространства) остаётся в ModelForm + CBV без сервиса.

## 4. URL structure

```
/                                             → редирект на /spaces/
/accounts/login/  /accounts/logout/           → аутентификация
/spaces/                                      → список доступных пространств
/spaces/create/                               → создание пространства
/spaces/<key>/                                → домашняя страница пространства
/spaces/<key>/settings/                       → настройки
/spaces/<key>/members/                        → участники
/spaces/<key>/pages/                          → плоский список страниц
/spaces/<key>/pages/create/                   → создание (?parent=<id>)
/spaces/<key>/pages/<slug>/                   → просмотр страницы
/spaces/<key>/pages/<slug>/edit/              → редактирование
/spaces/<key>/pages/<slug>/history/            → список версий
/spaces/<key>/pages/<slug>/history/<int:n>/   → просмотр версии
/spaces/<key>/pages/<slug>/attachments/       → вложения
/search/                                      → глобальный поиск

HTMX-эндпоинты (возвращают только фрагменты):
/spaces/<key>/tree/                           → поддерево (?parent=<id>)
/spaces/<key>/pages/<slug>/title/             → GET форма / POST сохранение заголовка
/spaces/<key>/pages/<slug>/move/              → POST перемещение
/spaces/<key>/pages/<slug>/comments/          → GET список / POST создание
/comments/<int:pk>/                           → PATCH / DELETE
/search/suggest/                              → живые подсказки поиска
```

Решения:

- `<key>` пространства в верхнем регистре, `<slug>` страницы — в нижнем.
  Пространство идентифицируется стабильным ключом, страница — slug (уникальным
  внутри пространства) с таблицей редиректов на случай переименования.
- HTMX-эндпоинты вынесены в отдельные пути, а не спрятаны под «тот же URL, но с
  заголовком `HX-Request`». Так проще и тестировать, и читать `urls.py`.
- Вложенность страниц **не отражается в URL** (`/pages/<slug>/`, а не
  `/pages/a/b/c/`). Иначе перемещение страницы в дереве меняет URL всех потомков,
  и любая внешняя ссылка ломается. Иерархия показывается через breadcrumbs.

Два уточнения:

- Фрагменты, которые нужны только одному шаблону (например, строка результата

  переиспользуется из нескольких мест или возвращается HTMX-эндпоинтом.
- `tree_item.html` рекурсивно включает себя же. Это нормально для Django-шаблонов
  при разумной глубине; дерево при этом строится в Python одним запросом, а не
  запросом на узел (см. раздел 6).

## 6. Дерево страниц

**Модель хранения: `parent` FK + `position`.** Никаких `django-mptt` или
`treebeard` в первой версии. Обоснование: узкое место tree-библиотек — быстрые
запросы поддерева на больших объёмах, а корпоративное пространство — это сотни,
максимум единицы тысяч страниц. При таком объёме дерево целиком читается одним
запросом, а стоимость поддержки MPTT (перестройка индексов при каждом
перемещении, риск разъехавшихся `lft`/`rght`) не оправдана.

**Рендеринг сайдбара — один запрос на всё дерево:**

```python
nodes = (Page.objects
         .filter(space=space, status=Page.Status.PUBLISHED)
         .only('id', 'title', 'slug', 'parent_id', 'position')
         .order_by('position', 'title'))
```

Далее группировка по `parent_id` в словарь и рекурсивный рендер из корней.
Итого: 1 SQL-запрос независимо от глубины и количества узлов, никакого N+1.

**Ленивая загрузка** включается, когда пространство перестаёт быть маленьким:
узел с детьми отдаёт `hx-get="/spaces/ENG/tree/?parent=<id>"`, ответ —
`tree_item.html` для детей. Порог (например, >500 страниц) определим по факту;
архитектура одинаковая, меняется только начальный набор загруженных уровней.

**Перемещение — `PageService.move_page(page, new_parent, position)`** в
`transaction.atomic()`:

1. Проверка, что `new_parent` в том же пространстве.
2. Проверка отсутствия цикла: поднимаемся по цепочке родителей `new_parent` и
   убеждаемся, что не встретили саму `page`. Ограничение БД от циклов не спасает
   (`CheckConstraint` ловит только `parent = self`), поэтому проверка обязательна
   в сервисе.
3. Пересчёт `position` у соседей.

**Порядок соседей:** целое `position` с шагом 100 и перенумерация соседей внутри
одного родителя при вставке. Дробное («fractional») индексирование без
перенумерации выглядит элегантнее, но усложняет отладку; при количестве соседей
в десятки штук перенумерация в транзакции стоит дёшево.

**Breadcrumbs:** подъём по `parent_id`. Глубина реальных вики-деревьев — 3–6
уровней, это 3–6 дешёвых запросов по первичному ключу, и они гарантированно
попадают в кэш. Денормализованные `path`/`depth` добавим, только если появятся
запросы «всё поддерево целиком» (например, каскадное архивирование или экспорт) —
это спорный вопрос №7.

**Удаление:** по умолчанию — архивирование. Родитель — `PROTECT`, так что
случайное удаление страницы с детьми невозможно; сервис требует явного решения:
либо перевесить детей на родителя удаляемой страницы, либо архивировать
поддерево.

## 7. Версии страниц

**Полный снимок в `PageVersion`, не diff и не JSON-поле в `Page`.**

Обоснование: страницы — это текст, снимок содержимого весит килобайты.
Восстановление версии превращается в копирование строки, а не в последовательное
применение патчей. Diff между произвольными версиями считается на лету
`difflib` из стандартной библиотеки, без зависимостей. Хранение истории внутри
одного JSON-поля лишило бы нас индексов, ограничений уникальности номера версии
и возможности сослаться на версию по FK.

**Создание версии — внутри сервиса, в транзакции, с блокировкой строки:**

```python
@transaction.atomic
def update_page(page, *, title, body, author, change_note=''):
    body = sanitize_html(body)           # санитизация до сравнения и записи
    page = Page.objects.select_for_update().get(pk=page.pk)
    if (title, body) == (page.title, page.body):
        return page                      # пустое сохранение не плодит версии
    page.version += 1
    page.title = title
    page.body = body
    page.text_content = html_to_text(body)
    page.updated_by = author
    page.save(update_fields=[...])
    PageVersion.objects.create(page=page, number=page.version, title=title,
                               body=body, body_format=page.body_format,
                               author=author, change_note=change_note)
    return page
```

`select_for_update()` нужен от гонки: два одновременных сохранения без него
получат одинаковый номер версии и упрутся в `UniqueConstraint` — это лучше тихой
порчи истории, но пользователь увидит ошибку вместо сохранения. Ещё одна причина
разрабатывать на PostgreSQL: на SQLite эта блокировка фактически ничего не
делает, то есть проблема не воспроизводилась бы до продакшена.

Заодно в этом же сервисе выполняется санитизация `body` и пересчёт
`text_content` и `search_vector` — все производные от контента поля обновляются в
одном месте, а не в `save()` модели и не в сигналах.

**Версия №1 создаётся при создании страницы** — история всегда полна, нет
особого случая «страница без версий».

**Восстановление создаёт новую версию** с содержимым старой, а не переписывает
историю. Это принципиально: история изменений в корпоративном инструменте
должна быть append-only, иначе она перестаёт быть доказательством.

**Ограничения MVP:** без версионирования перемещений в дереве и без версий
вложений. Версионируются заголовок и содержимое.

## 8. Permissions

Три уровня, от простого к сложному, и в MVP реализуются только первые два.

**1. Видимость пространства** — поле `Space.visibility`:
`INTERNAL` видно любому аутентифицированному сотруднику, `PRIVATE` — только
участникам. Анонимного доступа нет вообще: включаем
`LoginRequiredMiddleware` (Django 6.0), и всё закрыто по умолчанию, а страница
логина помечается `@login_not_required`.

**2. Роль в пространстве** — `SpaceMembership.role`:

| Действие | viewer | editor | admin | owner |
|---|---|---|---|---|
| Просмотр страниц | + | + | + | + |
| Комментирование | + | + | + | + |
| Создание/редактирование страниц | | + | + | + |
| Архивирование, перемещение | | + | + | + |
| Физическое удаление | | | + | + |
| Управление участниками | | | + | + |
| Настройки, удаление пространства | | | | + |

**3. Ограничения на отдельную страницу** (как в Confluence) — **вне MVP**, но
модель это допускает: добавляется `PageRestriction(page, user_or_role, level)`
и одна дополнительная проверка в уже существующей точке принятия решения.

**Реализация — один модуль чистых функций** `apps/spaces/permissions.py`:

```python
def get_role(user, space) -> Role | None      # с кэшированием на request
def can_view_space(user, space) -> bool
def can_edit_pages(user, space) -> bool
def can_delete_pages(user, space) -> bool
def can_manage_members(user, space) -> bool
```

плюс `SpaceAccessMixin` в `core`, который по `<key>` из URL достаёт пространство,
один раз получает роль и кладёт её в `request`. Одна дополнительная выборка на
запрос, дальше проверки бесплатны.

**Почему не `django-guardian`:** он хранит права построчно для каждого объекта.
Здесь право выводится из роли в пространстве — это один запрос и никакой
синхронизации таблиц прав при создании каждой страницы. Встроенные
Django-permissions используем только для админки.

**Правило, которое стоит зафиксировать сразу:** проверка прав живёт в views и
сервисах, но **никогда** в шаблонах в виде бизнес-логики. В шаблон приходит уже
готовый флаг (`can_edit`), а не вычисление роли.

## 9. Где именно использовать HTMX

**Использовать:**

| Сценарий | Механика |
|---|---|
| Inline-редактирование заголовка | `GET .../title/` → форма, `POST` → `page_title.html` |
| Дерево: раскрытие узла | `hx-get .../tree/?parent=<id>` → `tree_item.html` |
| Дерево: обновление после создания страницы | ответ создания отдачает новый `tree_item.html` |
| Перемещение страницы | `POST .../move/` → перерисовка затронутого поддерева |
| Комментарии: создать/изменить/удалить | ответ — `comment.html`, счётчик обновляется через `hx-swap-oob` |
| Живой поиск | `hx-trigger="keyup changed delay:300ms"` → `suggest.html` |
| Загрузка вложений | `hx-post` с `hx-indicator` для прогресса |
| Добавление/удаление участника | ответ — `member_row.html` |
| Подтверждения удаления | загрузка содержимого модального окна фрагментом |

**Не использовать** (обычный Django request/response проще и надёжнее):
просмотр страницы, полная форма редактирования содержимого, список пространств,
настройки пространства, страница истории версий, логин.

**Соглашения, которые задаём сразу**, чтобы потом не разгребать:

- HTMX-эндпоинт возвращает **только фрагмент** и осмысленный HTTP-код. Ошибка
  валидации — `422` с той же формой и текстами ошибок, а не `200` с тихим
  провалом.
- Никаких «частично HTMX» view: если эндпоинт из списка выше, он всегда отдаёт
  фрагмент. Определение через `request.headers.get('HX-Request')` оставляем как
  исключение, а не как основной приём.
- Побочные эффекты — через `HX-Trigger` (например, показать toast) и
  `HX-Redirect` вместо ручных редиректов в JS.
- `{% partialdef %}` из Django 6.0 даёт то, чего раньше приходилось добиваться
  внешним пакетом: разметка узла дерева описана один раз и используется и при
  полном рендере страницы, и как HTMX-ответ. Это устраняет главный источник
  расхождений между «первой отрисовкой» и «обновлением фрагмента».
- `htmx.min.js` кладём в `static/`, а не тянем с CDN: корпоративная сеть может
  быть изолирована, и версия должна быть воспроизводимой.

## 10. Где Alpine.js, а где обычный JS

**Alpine — только локальное состояние UI:**

- сворачивание сайдбара (с сохранением в `localStorage`);
- меню пользователя, меню действий над страницей и пространством;
- модальные окна (`<dialog>` + Alpine для управления открытием);
- табы в настройках пространства;
- раскрытие/сворачивание уже загруженных узлов дерева;
- горячие клавиши (`@keydown.window`), открытие командной палитры;
- мелкая обратная связь: «ссылка скопирована», tooltip.

**Alpine не используем** для хранения дерева страниц, содержимого страницы,
списка комментариев или флагов прав — источник истины только Django/БД.

**Обычный JS понадобится ровно в двух местах:**

1. **Drag & drop в дереве.** Нативный HTML5 DnD работает, но заметно неудобен на
   вложенных списках. Тут уместна небольшая специализированная библиотека
   (`SortableJS`, ~10 КБ) — это единственная фронтенд-зависимость, которую я бы
   защищал. Итог перетаскивания уходит обычным `POST` на `.../move/`.
2. **Textarea-эргономика в редакторе:** Tab/отступы, автоподстановка списков,
   вставка ссылки по Ctrl+K. Десятки строк своего кода, без библиотек.

## 11. Зависимости

**Уже есть:** Django 6.0.7 (+ транзитивные `asgiref`, `sqlparse`, `tzdata`).

**Обязательно, с этапа 0:**

| Пакет | Зачем | Можно ли без него |
|---|---|---|
| `psycopg[binary]` | драйвер PostgreSQL | нет — разработка идёт на PostgreSQL |
| `nh3` | санитизация HTML из редактора перед записью в `body` | **нет.** Контент приходит из браузера и выводится через `\|safe`; без allowlist-санитизации это хранимая XSS. Это Rust-биндинг к ammonia, быстрее и безопаснее устаревшего `bleach` |

Markdown-рендерер (`markdown-it-py` / `mistune`) из плана **исключён** — выбран
WYSIWYG, парсить Markdown не требуется.

**Только для разработки:**

| Пакет | Зачем | Комментарий |
|---|---|---|
| `ruff` | линтер + форматтер | заменяет black + isort + flake8 одним инструментом |
| `django-debug-toolbar` | видеть N+1 сразу | для дерева и списков комментариев это критично |

**Фронтенд-ресурсы** (файлы в `static/`, не пакеты Python):

| Что | Зачем | Замечание |
|---|---|---|
| `htmx.min.js` | фрагментные обновления | вендорим, не CDN: корпоративная сеть может быть изолирована |
| `alpine.min.js` | локальное состояние UI | то же |
| CKEditor 5 (ZIP, self-hosted) | редактирование страниц | `licenseKey: 'GPL'`; шаг сборки JS не нужен, файлы кладутся в `static/vendor/ckeditor5/` вместе с русской локализацией |
| `SortableJS` (~10 КБ) | drag & drop в дереве страниц | единственная фронтенд-библиотека, которую я считаю оправданной помимо перечисленного |

#### Что важно знать про интеграцию CKEditor 5

- Берём **self-hosted ZIP-дистрибутив**: GPL-ключ работает только с ним, через
  их облачный CDN он не принимается. Заодно это совпадает с общим принципом
  вендорить фронтенд-ресурсы.
- **Не используем пакет `django-ckeditor`** и вообще CKEditor 4: четвёртая
  версия давно снята с поддержки, а этот пакет ориентирован на неё. Интеграция
  делается вручную — это буквально одна форма, один `<div>` и инициализация.
- Редактор отдаёт **HTML**, поэтому серверный рендер блоков не нужен: пишем
  `body_format='html'` и прогоняем содержимое через `nh3` перед записью в `body`.
  Allowlist санитайзера составляем по фактически включённым плагинам, а не «на
  глазок»: всё, что редактор не умеет создавать, в разметке быть не должно.
- Загрузка изображений: штатный upload-адаптер отправляет файл на наш эндпоинт и
  ждёт в ответ JSON с адресом файла, а CSRF-токен передаётся через заголовки. Это
  и есть причина, по которой `Attachment` понадобился уже на этапе 3.
- Платные возможности (совместное редактирование, история ревизий, импорт-экспорт
  Word, AI) не подключаем: история версий у нас своя, серверная, и она надёжнее —
  не зависит от того, что происходило в браузере.
- При настройке CSP на этапе 10 нужно учесть, что редактору требуются inline-стили.

**Осознанно НЕ добавляем:**

- **Django REST Framework** — API некому потреблять: HTMX работает с HTML.
  Добавим, когда появится мобильное приложение или внешняя интеграция.
- **django-mptt / treebeard** — `parent` FK достаточно (раздел 6).
- **django-guardian** — права выводятся из роли (раздел 8).
- **Celery + Redis** — в Django 6.0 есть `django.tasks`.
- **django-htmx** — его основная польза (`request.htmx`) заменяется пятью
  строками своего кода.
- **django-environ** — `os.environ` + маленький хелпер закрывают задачу.
- **Elasticsearch / OpenSearch** — PostgreSQL FTS хватит на годы при таких
  объёмах.
- **Tailwind** — решено: свой CSS с дизайн-токенами (CSS custom properties), без
  этапа сборки.
- **TinyMCE, TipTap, Editor.js, Quill** — рассматривались как альтернативы
  CKEditor 5 и отклонены по итогам обсуждения. TipTap (MIT, на базе ProseMirror)
  был бы предпочтителен, если бы платформу планировали распространять за пределы
  организации, но он headless: панель инструментов пишется самостоятельно, и ему
  нужен шаг сборки JS. При внутреннем использовании CKEditor даёт готовый
  интерфейс, лучшую в классе вставку из Word и Excel и полноценные таблицы без
  сборки — при равной архитектуре на стороне Django.
- **Оговорка на будущее:** если платформу когда-нибудь решат продавать или
  передавать другой организации, вопрос лицензии CKEditor придётся открыть
  заново — понадобится коммерческая лицензия (self-hosted у них только через
  отдел продаж) либо переход на TipTap. Стоимость такого перехода намеренно
  оставлена низкой: меняются шаблон редактора и JS-бандл, схема БД — нет.
- **Pillow** — только когда понадобятся превью изображений.
- **whitenoise** — только на этапе деплоя.

## 12. План реализации по этапам

Этапы небольшие, каждый заканчивается работающим состоянием.

**Этап 0. Фундамент** (без бизнес-функций)
`docker-compose.yml` с PostgreSQL, `psycopg`, разделение настроек
(`base`/`dev`/`prod`), секреты из переменных окружения, удаление `apps/wiki`,
`TEMPLATES['DIRS']`, `STATICFILES_DIRS`, `MEDIA_ROOT`, `LANGUAGE_CODE`/`TIME_ZONE`,
`.gitignore`, `ruff`, `base.html` с каркасом и дизайн-токенами, htmx + Alpine в
`static/`, логин/логаут, `LoginRequiredMiddleware`.
*Готово, когда:* проект поднимается на PostgreSQL, можно войти в систему и
увидеть пустой каркас интерфейса.

**Этап 1. Модели `spaces` + `pages`**
`Space`, `SpaceMembership`, `Page`, `PageVersion` (без комментариев и вложений),
`search_vector` + `GinIndex` сразу, админка, миграции, фабрики для тестов.
*Готово, когда:* пространства и дерево страниц создаются через админку.

**Этап 2. Чтение**
Список пространств, домашняя страница пространства, просмотр страницы,
сайдбар с деревом (один запрос), breadcrumbs, вёрстка рабочего интерфейса.
*Готово, когда:* по вики можно навигироваться; Debug Toolbar не показывает N+1.

**Этап 3. Запись + версии + редактор**
Создание/редактирование/архивирование страниц, ModelForms, `PageService`,
генерация slug, `PageRedirect`, создание `PageVersion` на каждое сохранение,
подключение CKEditor 5 с русской локализацией, санитизация через `nh3`,
извлечение `text_content`.

Вместе с редактором приходится сделать и **модель `Attachment` с эндпоинтом
загрузки**: инструмент вставки изображения требует адреса, куда загружать файл, и
ждёт в ответ JSON со ссылкой. Поэтому вложения переехали с этапа 9 сюда — это
прямое следствие решения о WYSIWYG. Полноценный интерфейс списка вложений
остаётся на этап 9, здесь нужен только загрузчик.

*Готово, когда:* страница создаётся и правится в редакторе, история пишется,
изображение вставляется в текст.

**Этап 4. Права**
`permissions.py`, `SpaceAccessMixin`, проверки во всех views и сервисах, UI
участников. Сознательно **раньше** комментариев и поиска: встраивать
авторизацию в готовую систему дороже и рискованнее, чем писать с ней сразу.
*Готово, когда:* viewer не может править, не-участник не видит приватное
пространство, и это покрыто тестами.

**Этап 5. HTMX-слой**
Inline-заголовок, ленивое дерево, перемещение (включая drag & drop), модальные
подтверждения.
*Готово, когда:* типовые действия не перезагружают страницу.

**Этап 6. История версий в интерфейсе**
Список версий, просмотр версии, восстановление, diff через `difflib`.

**Этап 7. Комментарии**
Модель, CRUD на HTMX, мягкое удаление.

**Этап 8. Поиск**
PostgreSQL FTS по `title` и `text_content`, обновление `search_vector` в
сервисе сохранения, ранжирование, фильтр по пространству, живые подсказки.
Абстракция «двух бэкендов поиска» **не нужна** — это прямая выгода от решения
разрабатывать на PostgreSQL.

**Этап 9. Вложения — интерфейс**
Список вложений страницы, удаление, отдача файлов через view с проверкой прав
(файлы приватных пространств не должны быть доступны по прямой ссылке на
`MEDIA_URL`). Сама модель и загрузчик уже сделаны на этапе 3.

**Этап 10. Полировка**
Доступность (фокус, ARIA, контраст), клавиатурная навигация, пустые состояния,
`ContentSecurityPolicyMiddleware` для страниц с пользовательским HTML,
чек-лист продакшена.

Порядок этапов 1–4 я бы менять не советовал; 5–9 можно тасовать по интересу.

### Про миграции

Пока в базе нет данных и никто не пользуется системой, миграции обычные —
блокировки некому мешать. Правила `django-safe-migration` начинают действовать с
момента первого деплоя с реальными данными и пользователями: `AddIndexConcurrently` вместо `AddIndex`,
`db_default` для `NOT NULL`, FK через `NOT VALID` + `VALIDATE`,
`SET LOCAL lock_timeout` перед операциями с `ACCESS EXCLUSIVE`,
`SeparateDatabaseAndState` для удаления полей. Это стоит зафиксировать в
`AGENTS.md` вместе со стратегией деплоя, чтобы дальше проверялось автоматически.

## 13. Спорные решения

### Решено 2026-08-09

1. **`apps/wiki`** — удаляем приложение вместе с миграцией, создаём `spaces` +
   `pages` с нуля. Данных нет (0 пространств, 0 страниц), терять нечего.
2. **Контент** — сразу готовый WYSIWYG-редактор.
3. **БД** — PostgreSQL локально в Docker с самого начала.
4. **CSS** — свой, с дизайн-токенами, без сборки.
5. **Аутентификация** — только логин с паролем, SSO не планируется.
6. **Удаление** — архивирование по умолчанию для страниц и пространств;
   физическое удаление доступно только роли admin/owner и только с явным
   подтверждением каскада на поддерево.
7. **Редактор — CKEditor 5**, self-hosted ZIP в `static/`, `licenseKey: 'GPL'`.
   Платформа остаётся внутренним инструментом и никому не передаётся, поэтому
   обязательства GPL не возникают (они срабатывают при распространении, а не при
   использовании). Надпись «Powered by CKEditor» остаётся в интерфейсе.
   Контент хранится как HTML (`body_format = 'html'`).

### Практические следствия двух последних решений

**A. Выбор редактора** — CKEditor 5, детали интеграции в §11.

**B. Архивирование вместо удаления.** У `Page` и `Space` есть `is_archived`, менеджер по
умолчанию отдаёт только неархивированные записи (архив доступен через явный
`Page.objects.with_archived()`), `on_delete=PROTECT` на `space` и `parent`
страхует от случайного каскада, а физическое удаление живёт отдельным методом
сервиса с проверкой роли.

### Мелкие решения, которые я приму по умолчанию

Если возражений нет, действую так. Каждое из них дешево изменить позже.

1. **Денормализация `path`/`depth` в дереве** — не добавляю, хватает `parent` FK.
   Добавим, если появятся операции над целым поддеревом.

5. **Версия PostgreSQL в Docker** — актуальная стабильная (17). Назовите другую,

## Итог

Из существующего кода в целевую систему переходят виртуальное окружение,
`accounts.User` с `AUTH_USER_MODEL` и стиль кода; остальное проектируется заново.
Стек закрывает задачу без лишних зависимостей: Django 6.0 принёс встроенные
шаблонные partials (идеально ложатся на HTMX), фоновые задачи и
`LoginRequiredMiddleware`, поэтому список пакетов Python сводится к `psycopg` и
`nh3` плюс два инструмента разработки.

Принятые решения сместили три вещи в плане: PostgreSQL с этапа 0 (и, как
следствие, отсутствие абстракции над двумя бэкендами поиска), поисковый вектор
уже в первой миграции, а загрузка вложений переехала с этапа 9 на этап 3, потому
что её требует инструмент вставки изображений в редакторе.

Выбор CKEditor 5 вместо изначально рекомендованного TipTap убрал из проекта Node
и написание собственной панели инструментов, а взамен добавил единственное
условие — надпись «Powered by CKEditor» в интерфейсе и возврат к вопросу
лицензии, если платформу когда-нибудь решат распространять. Django-сторона от
выбора редактора не зависит: `body` + `body_format` + `text_content` подойдут
любому из рассмотренных вариантов.
