Django отвечает за бизнес-логику и данные.

Django Templates отвечают за server-side rendering.

HTMX используется для взаимодействия с сервером без полной перезагрузки страницы:
- формы;
- inline editing;

- обновление дерева страниц;
- поиск;
- фильтрация;
- подгрузка контента;
- модальные действия;
- небольшие динамические части интерфейса.

Alpine.js используется для локального состояния UI:
- dropdown;
- modal;
- sidebar;
- tabs;
- tooltip;
- раскрытие/скрытие элементов;
- локальные переключатели;
- keyboard shortcuts.

Не использовать Alpine как замену полноценному backend state management.

Если появится задача, которую разумнее решить небольшой специализированной JS-библиотекой,
можно предложить её отдельно.

2. ИДЕЯ ПРОДУКТА
==================================================

Основная сущность верхнего уровня — Workspace / Space.

Пример:

Engineering
├── Backend
│   ├── Django conventions
│   ├── API documentation
│   └── Deployment
│
├── Frontend
│   └── UI guidelines
│
└── Architecture
    └── System overview

Внутри Space пользователь создаёт страницы.

Страницы должны поддерживать древовидную структуру:

Page
├── Child page
│   └── Child page
└── Child page

У страницы могут быть:

- заголовок;
- содержимое;
- родительская страница;
- Space;
- автор;
- дата создания;
- дата последнего изменения;
- статус;
- версия;
- slug / URL identifier;
- порядок среди соседних страниц.

Продумай модель так, чтобы дерево страниц можно было удобно выводить,
перемещать и расширять в дальнейшем.

Не нужно сразу внедрять сложные tree-библиотеки, если обычной модели parent FK достаточно
для первой версии.

5. DJANGO ARCHITECTURE
==================================================

Перед изменениями изучи текущую структуру проекта.

Не создавай новые слои только ради архитектурной красоты.

Но избегай огромных views.py.

Если бизнес-операция начинает быть сложной,
можно использовать service layer.

Например:

services/
    pages.py

с операциями вроде:

PageService.create_page(...)
PageService.move_page(...)
PageService.restore_version(...)
PageService.archive_page(...)

Однако простые CRUD операции не нужно искусственно выносить
в отдельные сервисы.

Используй:

- ModelForm там, где это удобно;
- Django permissions там, где они подходят;
- transactions для операций, требующих атомарности;
- select_related / prefetch_related при необходимости;
- constraints на уровне БД для важных инвариантов.

Избегай:

- fat views;
- сложной бизнес-логики в templates;
- signals без необходимости;
- строковых magic values;
- дублирования запросов;
- N+1;
- преждевременной абстракции.

==================================================
7. HTMX
==================================================

HTMX должен использоваться там, где он реально упрощает интерфейс.

Примеры:

создание страницы:

POST
/spaces/ENG/pages/create/

→ Django

→ возвращает новый tree_item.html

→ HTMX добавляет его в sidebar.

Редактирование title:

GET edit fragment
→ input

POST title
→ сохранение

→ возвращается обычный заголовок.

Комментарии:

POST comment
→ создаётся Comment
→ возвращается comment.html
→ добавляется в список.

Не превращай каждый endpoint в HTMX endpoint.

Обычный Django request/response там, где он проще,
остаётся предпочтительным.
